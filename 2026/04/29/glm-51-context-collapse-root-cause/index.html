从社区困惑到工程真相：GLM-5.1 上下文崩溃根因完整揭秘

过去几周，GLM-5.1 的用户们反复遇到同一个问题：对话超过 10 万 token 后，模型突然开始”发疯”——输出乱码、重复推理、甚至说出不着边际的生僻字。一时间社区里众说纷纭，有人怀疑是模型本身的长上下文能力缺陷，有人猜测是服务商在暗中降级，还有人怪罪于”量子波动速读”。

然而，真相远比猜测更精彩。

最近，一篇来自推理一线的工程实践文章揭开了谜底。那些让社区困惑不已的异常现象，不是模型的问题，而是推理系统里的两个底层竞态 Bug。本文将串联社区观察与工程调查，还原这个问题的完整链条。

社区的困惑：100K 魔数

4 月下旬，GLM-5.1 开源的消息登上了 Hacker News 热榜。这个 754B 参数（40B 活跃）的 MoE 模型在编程和 Agent 任务上表现亮眼，但讨论中反复出现一个令人不安的话题：上下文窗口在高 token 场景下不稳定。

官方标称 200K token 的上下文窗口，在实际使用中却呈现出诡异的”魔数”现象。

HN 上的用户描述了三种反复出现的症状：

第一种：突发性输出崩塌

“It goes from perfectly level headed working fine to all of a sudden just total breakdown, hard switch, at such a predictable context window size.” — HN 评论

模型从正常输出突然变为无意义字符流，没有渐进退化的过程，仿佛有人按下了开关。

第二种：循环重复

来自 GitHub Issue（opencode #17981 ):

“When the context approaches the 100k token mark, the agent will ask a question, we respond and it will start going through a reasoning process that it already did in the past and will ask the same question again.” — GitHub Issue 报告

模型开始重复之前已经完成的推理过程，像是陷入了时间循环。

第三种：逐步退化后无法恢复

“When you crest 128k tokens, there’s a high chance that the model will start spouting gibberish until you compact the history.” — HN 评论

并非所有用户都经历”硬开关”式的崩塌，也有渐进退化的报告，但最终结果一样——上下文变成一锅粥。

更令人困惑的是，这个”魔数”并不固定。有人观察到崩溃阈值从 60K 漂移到 100K 再到 200K，不同时段、不同地区、不同套餐等级的用户体验截然不同。HN 上有用户一针见血地猜测：

“It seems so so probable to me that this isn’t the model that’s making this happen: it’s the hosting. There’s some KV cache issue, or they are trying to expand the context window in some way.”

KV Cache 问题——这个来自社区的直觉猜测，最终被工程团队的排查证实了。

工程团队的调查：从现象到根因

与社区的猜测不同，推理工程师们选择了系统的排查方法。

他们首先对用户反馈的 Bad Case 做本地回放，将同一批请求重复推理数百次，但始终未能复现异常。这个”与请求内容无关、与系统压力相关”的特征，立即将嫌疑指向了推理基础设施而非模型权重本身。

为了进一步模拟线上环境压力，团队对线上日志做脱敏处理，尽可能保留原始并发分布与请求时序，在本地进行全量回放。起初仍未复现，直到调整 PD 分离比例并持续提高系统负载，模拟高峰期的 Prefill 堆积和 Decode 侧 KV Cache 压力后，才在约每万次请求中稳定复现 3-5 次异常。

这确认了问题的方向：高负载下的推理状态管理出了问题。

意外发现：投机采样指标成为”异常探测器”

在反复分析推理日志后，团队发现了一个意想不到的切入点——投机采样（Speculative Decoding）指标。

投机采样原本是一个性能优化技术：先由草稿模型生成候选 token，再由目标模型校验并决定是否接受。工程师们发现，这个指标的数值在异常发生时呈现出稳定模式：

  • 乱码和生僻字：通常伴随极低的 spec_accept_length（目标模型连续接受的 draft token 前缀长度），表明草稿模型生成的候选 token 几乎全部被目标模型拒绝——这意味着目标模型所看到的 KV Cache 状态与草稿模型预期之间存在显著偏差。

  • 复读：通常伴随偏高的 spec_accept_rate（draft token 被接受的比例），表明损坏的 KV Cache 可能使注意力模式退化，并将生成过程推向高置信度的重复循环。

基于这些观察，团队实现了一套在线异常监控策略：当 spec_accept_length 持续低于 1.4 且生成长度已超过 128 token，或 spec_accept_rate 超过 0.96 时，系统主动中止当前生成并重试。投机采样从单纯的性能优化技术，华丽转身为输出质量的实时监控信号。

BugFix #1 ：PD 分离架构下的 KV Cache 竞态

第一个 Bug 藏在 PD（Prefill-Decode）分离架构中。

问题根源：异步 Abort 引发的 KV Cache 复用竞态

为限制尾延迟，推理引擎引入了基于超时的请求终止机制：当 Prefill 阶段未在规定时间内完成时，Decode 侧会对请求执行 Abort，并回收其占用的 KV Cache 资源。

然而，Abort 信号未被正确传播至 Prefill 侧。同时，Decode 侧也缺乏判断 KV Cache 是否可安全回收与复用的充分信息。

时序是这样的：

  1. Req1 被发送至 Prefill-1（P1）和 Decode（D）
  2. 由于调度或排队等原因，Req1 在 P1 侧经历了一段等待后才开始执行 Prefill Forward
  3. Decode 侧在一段时间内未收到对应的 KV Cache 数据，触发超时机制，对 Req1 执行 Abort
  4. Decode 侧回收 Req1 占用的 KV Cache 槽位，但没有正确通知 P1
  5. 新请求 Req2 到达，被分配到与 Req1 相同的 KV Cache 地址（内存复用策略）
  6. P2 开始执行 Prefill Forward 并进行 KV Transfer，Decode 侧进入生成阶段
  7. 与此同时，P1 侧针对 Req1 发起的 KV Cache 写入仍在继续，写入已被 Req2 复用的显存区域，覆盖 Req2 的部分 KV Cache
  8. Req2 在 Decode 阶段读取到被覆盖的数据，生成结果异常

这就是社区用户观察到的乱码、复读、生僻字的直接原因——跨请求的 KV Cache 数据污染。

修复方案：KV Cache 释放的时序一致性保证

解决方案是在请求终止与 KV Cache 写入完成之间建立显式同步关系：

  • Decode 在触发 Abort 后，向 Prefill 侧发送通知
  • Prefill 仅在以下条件满足时返回”可释放”信号：相关 RDMA 写入尚未开始，或所有已提交写入均已完成
  • Decode 仅在收到该确认后，才允许回收并复用对应的 KV Cache 槽位

修复效果：异常输出的发生率由约万分之十几下降至万分之三以下。

BugFix #2 ：HiCache 加载时序缺失

第二个 Bug 与 HiCache（多级 KV Cache）有关。

问题根源：流水线同步缺失导致的 Read-Before-Ready

Coding Agent 场景显著提高了输入长度（平均超过 70K tokens），同时伴随较高的前缀复用率。这使得 HiCache 成为线上服务中的关键优化手段。

然而，在 KV Cache 换入与计算重叠执行的情况下，系统未能保证数据在使用前已完成加载，导致可能出现未就绪 KV Cache 被访问的情况。

问题出在 DSA HiCache 的缓存读取路径上：系统会从 CPU 内存异步换入历史前缀缓存，并通过 Load Stream 与 Forward Stream 的重叠执行来提高吞吐。理论上，Forward Stream 中的 Indexer 计算应在对应的 Indexer Cache 完成加载后才能启动。但在原始实现中，该依赖未被显式表达——Indexer 算子启动时未对 Load Indexer Cache 的完成建立同步约束，导致 Forward Stream 可能先于 Load Stream 完成数据加载而开始执行。

这就是”Read-Before-Ready”访问模式——数据尚未完成加载时即被读取，导致后续计算基于不完整或未初始化的数据。

修复方案：重构算子流水线的原子性

修复方案在数据加载与计算之间引入显式同步约束：

  • 在 Indexer 算子启动前引入与 Load Stream 的同步点，确保对应层级的 Indexer Cache 已完成加载
  • Forward Stream 仅在数据就绪后才启动计算

这个修复已通过 SGLang Pull Request #22811 提交至开源社区。

一张图理解两个 Bug 的关联

如果用一句话总结两个 Bug 的共同特征，那就是：在高并发、长上下文的 Coding Agent 场景下，推理系统的状态一致性被打破了。

维度 Bug #1: KV Cache 竞态 Bug #2: HiCache 时序
问题本质 跨请求的 KV Cache 数据覆盖 单请求内的数据未就绪被访问
触发条件 PD 分离架构 + 超时 Abort HiCache 换入与计算重叠执行
异常表现 乱码、复读、生僻字 同上
根因关联 spec_accept_length 极低 同上
修复收益 万分之十几 → 万分之三 完全消失

两个 Bug 都只在高并发 + 长上下文的特殊场景下触发，这就是为什么普通对话测试无法复现、为什么社区用户反馈”不稳定”但”不是每次都出问题”。

对开发者的启示

1. “模型不行”和”系统不行”是两码事

当你在使用 GLM-5.1 时遇到乱码或复读，第一反应可能是”模型的长上下文能力有缺陷”。但更多时候，这可能是推理基础设施在特定压力下的 transient failure。主动压缩上下文（如 /compact 命令）是有效的临时方案，因为它降低了触发 Bug 的概率。

2. 投机采样不只是加速器

SGLang 团队发现的 spec_accept_length 与输出质量的相关性，是一个很有价值的工程洞察。在生产环境中监控这个指标，可以在用户感知到异常之前提前发现系统问题。

3. 长上下文场景下的系统工程挑战

这两个 Bug 揭示了一个更深层的现实：在追求更长上下文窗口的过程中，推理系统工程面临着前所未有的挑战。KV Cache 的容量管理、跨请求的状态隔离、多级缓存的一致性保证——每一个环节都可能出现微妙的竞态条件。

总结

回到最初的问题：GLM-5.1 在 100K token 后崩溃，是模型的问题吗？

不是。

这是推理基础设施中的两个独立 Bug： - PD 分离架构下的 KV Cache 竞态，导致跨请求的数据污染 - HiCache 加载时序缺失，导致数据未就绪被访问

好消息是，这两个 Bug 都已被修复，修复方案也已开源。坏消息是，在高并发、长上下文的 Coding Agent 场景下，这类问题可能还会以其他形式出现。

当模型的能力越来越强大时，支撑它的系统工程也需要同步进化。Scaling Law 不仅驱动模型参数的膨胀，也在不断逼近 Infra 工程的极限。这场”Scaling Pain”，可能才刚刚开始。
