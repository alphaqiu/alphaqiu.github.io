76000 行代码、118 个慢 446 倍的函数：Claude Code 写的代码你敢直接上线吗？

一次用数据说话的”控诉”

4 月 2 日，GitHub 上出现了一个不寻常的 Issue。开发者 stellaraccident 没有粘贴报错日志，也没有描述复现步骤——他提交的是一份量化研究报告。

团队分析了 6852 个 Claude Code 会话文件，涵盖 17871 个思考块和 234760 次工具调用，时间跨度从 1 月到 3 月。结论直白到刺眼：2 月 12 日之后，Claude Code 在复杂工程任务上的质量崩了。

这个 Issue 在一周内收获了 950 个点赞和 264 颗心。同期，它在 Hacker News 上获得超过 1000 分，引发了一场关于 AI 编程工具真实能力的社区大辩论。

质量暴跌的背后：思考深度缩水 67%

这份分析报告最有价值的部分，在于它精准定位了问题的根源——extended thinking（扩展思考）的深度骤降。

Claude 的 extended thinking 机制类似人类工程师”先想清楚再动手”的习惯。在做复杂的多文件修改之前，模型会先在思考空间里规划：应该读哪些文件、按什么顺序、遵循哪些项目约定。这种深度思考，正是处理复杂工程任务的关键能力。

数据揭示了一个清晰的断层：2 月 12 日，Anthropic 上线了 redact-thinking-2026-02-12 功能，将思考内容从用户界面中隐藏。表面上这只是一个 UI 变更——Anthropic 后来在 HN 上解释，这并不影响思考本身。但 stellaraccident 的数据显示，思考深度在 2 月底已经下降了约 67%。

更关键的是行为模式的变化。思考深度降低后，Claude 的工具使用策略从”研究优先”转向了”编辑优先”——不再先充分阅读和理解代码，而是直接动手修改。报告里有一句话精准概括了这种变化带来的后果：

“模型默认采取成本最低的行动：选择最简单的修复而非正确的修复。”

这正是大量开发者报告的典型症状：Claude 开始忽略指令、声称进行了”最简单的修复”但实际上是错误的，甚至做出与要求完全相反的操作。

不只是思考的问题：工程层面的”连锁崩塌”

如果说思考深度下降是质量退化的根本原因，那么围绕 Claude Code 的工程问题则是让开发者愤怒的直接导火索。

GitHub issue 列表里，一连串的高赞 bug 报告勾勒出一个令人沮丧的画面：

无限压缩循环。当会话超过一定长度，Claude Code 触发自动压缩（compaction），反复重试最多 10 次后彻底冻结，所有进度丢失。一位开发者描述：“它 stuck 在无限循环里，反复读取同样的 5 个测试文件，既不创建新文件，也不执行任何操作。”

内存爆炸。开发者 christianromney 在详细诊断中发现，恢复大型会话时，Claude Code 会在 26-39 秒内吃满 CPU，内存飙升至 7-11GB，最终以一连串 tengu_uncaught_exception 崩溃收场。一个 JavaScript 运行时出现了 heapUsed > heapTotal 的不可能状态。

子代理崩溃。在使用 Task 工具生成子代理并行工作时，JSON 序列化阶段触发 100% CPU 死锁，必须强制杀进程。这个 bug 在 2025 年 7 月就被报告，点赞 38，至今仍被开发者反复提及。

上下文增长导致的卡顿。当上下文积累到 1000 条左右，终端输入开始明显延迟；到 15000 条时，基本无法操作。一位用户直白地说：“它坏到甚至不好笑了。”

社区的分化：从”神器”到”不可用”

这场讨论最有趣的部分，不是抱怨本身，而是社区的分化。

一方是重度用户。stellaraccident 的团队运营着 50+ 个并发 Claude Code 会话，做系统级编程（C、MLIR、GPU 驱动）。在”好”的时期，他们一个周末就合并了两个 PR、191000 行代码。这种使用强度下，任何退化都是灾难性的。

另一方是轻量用户。他们在 HN 上反驳：“我一直用得很好啊。”这种分歧并不矛盾——简单任务和复杂任务对工具的要求完全不同。写一个 React 组件和重构一个百万行 C++ 代码库，是两个维度的工程挑战。

一个来自 Reddit 的案例特别能说明问题。团队 Codeflash 用 Claude Code 构建了 76000 行代码（Java 语言支持和 React 框架支持），然后做了性能基准测试。结果发现：118 个函数运行速度比必要速度慢了最高 446 倍。

所有代码都通过了测试，在正常代码审查中也不会被发现。

这不是 Claude Code 独有的问题——所有大语言模型都倾向于生成”能跑的代码”而非”高性能代码”。但当你在生产环境中运行这些代码时，成本会在数月后的云账单上显现。

更深层的信号：AI 编程的边界正在被重新定义

这场争论实际上揭示了一个比 “Claude Code 好不好用” 更重要的问题：我们对 AI 编程工具的期望是否合理？

METR 的一项研究发现，经验丰富的开发者使用 Claude Code 完成复杂任务时，比不用工具慢了 19%。这不是因为工具没用，而是因为复杂任务需要深度的上下文理解、系统级的架构判断和细粒度的质量控制——这些恰恰是当前 AI 的薄弱环节。

Anthropic 的 Claude Code 创建者 Boris Cherny 在 HN 上做了部分回应，承认 2 月的两项变更（Opus 4.6 上线后的自适应思考默认值调整、思考内容隐藏）对部分用户造成了影响。团队随后上线了”effort”参数，允许用户手动调高思考深度。

但问题的核心不在于参数调节，而在于一个结构性矛盾：

商业模型追求降低成本（减少思考 token），而复杂工程恰恰需要更深的思考。

这两条路径在根本上是冲突的。

对开发者的实际启示

如果你正在使用或考虑使用 AI 编程工具，这场讨论提供了几个有价值的经验：

区分任务类型。 AI 编程工具在样板代码生成、调试辅助、代码库探索等场景中确实高效。但对于涉及跨模块架构决策、性能优化、大规模重构的复杂工程任务，当前的工具链还不够可靠。

关注上下文管理。 stellaraccident 的数据表明，思考深度对输出质量有决定性影响。尽量将大任务拆分为小步骤，每步结束后重新开始新会话，而不是在一个超长会话中持续工作。

不要跳过代码审查。 Claude Code 生成的代码能通过测试不代表它正确。Codeflash 的案例证明，性能问题完全隐藏在表面正确的代码之下。对生产代码进行独立的性能基准测试和架构审查，仍然不可替代。

工具选择取决于场景。 社区的共识正在形成：没有一种 AI 编程工具能覆盖所有场景。Claude Code 擅长终端原生工作流和快速原型，Cursor 更适合 IDE 内的多文件编辑，Codex 在复杂推理任务上表现更优。根据实际需求组合使用，比押注单一工具更务实。

AI 编程工具的未来毫无疑问是光明的。但承认当前的边界，不盲目夸大能力，是让这些工具真正产生价值的前提。正如一位 HN 用户所说：

“你越紧密地将工作流耦合到这些工具上，你就越依赖它们；而它们一旦失败，失望就越大。它们总是会失败的——区别只在于你要工作多久、做多复杂的事。”

与其争论 AI 编程”能不能用”，不如更精确地问：在什么条件下、对什么类型的任务、用什么方式使用，才能真正提升工程效率？ 这个问题的答案，比任何评测排名都更有价值。
