为什么 OpenAI、Anthropic、Google 都在用的底层库，自己跑出来做 Agent 框架了？

上周翻 GitHub Trending，一个熟悉的名字又冲上了热榜——pydantic-ai，目前 14,000+ Star，月下载量突破 220 万次，在 2026 年 Top AI Agent 框架榜单中稳居前十。

让我意外的不是它火了，而是它的作者。这个框架背后的团队，正是 Pydantic 的原班人马。如果你写过 Python，大概率绕不开他们：OpenAI SDK 的数据验证层是他们写的，Anthropic SDK、Google ADK、LangChain、CrewAI、LlamaIndex……几乎你能想到的所有 Python AI 项目，底层都用 Pydantic 做数据校验。

现在，这群造轮子的人决定自己造一整车。

它和 Pydantic 本身的类型系统是怎么打通的？

要理解 PydanticAI，先得理解 Pydantic 的核心逻辑。

Pydantic 做的事情很简单：在 Python 类型提示的基础上，自动校验数据类型。你定义一个 class User(BaseModel)，它会自动把 {"name": "Tom", "age": 25} 转换成带类型的 Python 对象。如果数据类型不对，它会在进入函数之前就报错，而不是等到运行时才爆炸。

PydanticAI 把这套逻辑搬进了 Agent 开发。核心机制是这样的：

LLM 每次返回数据后，PydanticAI 会： 1. 解析：把 LLM 的输出解析成结构化数据 2. 验证：用你定义的 Pydantic Model 校验每一个字段 3. 重试：如果验证失败，自动让 LLM 重试（框架会自动把错误信息喂给模型）

这就是他们说的”Validation 机制”——数据不符合约束？不好意思，退回去重做。

30+ 模型是统一抽象层还是各玩各的？

PydanticAI 的模型层不是”各玩各的”。它定义了一个标准接口，任何模型提供商只需要实现这个接口，就能无缝接入：

这意味着： - 换模型不用改业务逻辑 - 工具定义是模型无关的 - 同一套代码可以从 OpenAI 切换到 DeepSeek

当前支持 30+ 提供商：OpenAI、Anthropic、Gemini、DeepSeek、Groq、Ollama、通义千问、GLM、KIMI……对国内开发者非常友好。

它到底解决了什么痛点？

痛点一：类型安全终于不是空话了

在 LangChain 或原生 SDK 里写 Agent，你经常面对的是 Any 类型的返回值。运行时才发现 JSON 结构不对，是家常便饭。PydanticAI 从接口层面就绑定了类型：

如果 LLM 返回的数据不符合 SupportOutput 的约束，框架会自动提示模型重试。编译时就能发现的错误，不会拖到线上才爆炸。这种”如果编译通过就能跑”的体验，团队直说是在模仿 Rust 的哲学。

痛点二：Agent 不是写不出，是写出来没人敢上线

生产环境 Agent 最怕什么？黑盒。LLM 调了三轮工具、做了两次反思、中间某个参数还写错了——你事后根本还原不了过程。

PydanticAI 深度集成了自家的 Logfire 可观测性平台（基于 OpenTelemetry），每一步工具调用、模型推理、数据校验都被记录和追踪。用他们官方的话说：

“即使只有几个工具的简单 Agent，也可能与 LLM 产生大量来回交互，光看代码根本无法确认到底发生了什么。”

痛点三：框架绑架模型

2024 年不少团队被 LangChain 绑定，换模型痛苦不堪。PydanticAI 从第一天就做了模型无关设计，当前支持 30+ 模型提供商：OpenAI、Anthropic、Gemini、DeepSeek、Groq、Ollama、通义千问……甚至自定义模型只需实现一个接口。

对国内开发者来说，DeepSeek、KIMI、GLM 等国产模型都能通过 OpenAI 兼容协议直接接入，知乎上已有开发者用 DeepSeek V3 + PydanticAI 搭建了完整的客服系统，代码量比原生 SDK 少了将近一半。

2026 年势头为什么这么猛？

  • 迭代速度惊人：最新版本 v1.77.0，发布于 2026 年 4 月 2 日。平均每周发布一次，项目从 2024 年底公开发布到现在，版本号已经逼近 V2（V1 正式版于 2025 年 9 月发布）
  • 功能覆盖全面：MCP 协议支持、A2A（Agent 到 Agent 通信）、Durable Execution（持久化执行）、评估系统、Human-in-the-Loop 审批流程——这些功能在其他框架里通常要拼凑多个库才能实现
  • 月下载量 220 万+：说明真实开发者在用
  • 中文生态友好：Pydantic 官方维护了完整的中文文档站 ai.pydantic.org.cn，火山引擎（字节跳动云平台）开发者社区也在推广这个框架
  • 企业采纳信号：腾讯云社区文章提到，某金融科技公司采用后数据相关错误减少 95%，开发周期缩短 60%

但它不是银弹

客观讲几个不足：

生态还不够厚。 LangChain 有 80,000+ Star 和庞大的插件生态，PydanticAI 的第三方集成还比较有限。 V2 大版本即将到来。 根据官方版本策略，V2 最早 2026 年 4 月发布，可能引入 Breaking Changes。现在上生产的话，需要关注迁移成本。 学习资源以英文为主。 虽然有中文官方文档，但深度教程和踩坑经验仍然集中在英文社区。

V2 来了：现在上生产要注意什么？

PydanticAI V2 预计 2026 年 4 月发布。根据官方文档，V2 会有 Breaking Changes，但会提供至少 6 个月的 V1 安全维护期。

我的建议： - 如果是新项目，直接上 PydanticAI，用 V1 - 如果已有 LangChain 项目，评估迁移成本后再决定 - 关注官方升级指南，他们会提供平滑迁移路径

我对 PydanticAI 的判断

它能撼动 LangChain 吗？短期内不能，长期有可能。 PydanticAI 的核心竞争力不在功能数量——论功能丰富度它暂时还追不上 LangChain。 它的核心优势是工程可信度。

理由： - LangChain 生态太强：80,000+ Star，插件无数，教程铺天盖地 - PydanticAI 定位不同：它不是要做”另一个 LangChain”，而是做”生产级的 LangChain”

我的选型建议：

Pydantic 团队过去几年证明了一件事：他们能把数据验证做到 Python 生态的基础设施级别。现在他们把同样的严谨性带到 Agent 开发领域。如果你的项目对数据准确性有硬性要求（金融、医疗、法律），这个框架值得认真评估。

场景 推荐
金融/医疗/法律等强数据准确性要求 PydanticAI
快速原型/POC/周末项目 LangChain / OpenAI Agents SDK
多 Agent 协作复杂场景 LangGraph（更成熟）
个人开发者/中小团队 PydanticAI（学习曲线平缓，文档好）
低延迟实时对话 两者性能接近，但 PydanticAI 可观测性更强

如果你只是想快速搭个 Demo 或者做个周末项目，LangChain 或 OpenAI Agents SDK 可能上手更快。但如果你在构建一个需要上线的生产级 Agent 系统，PydanticAI 提供的类型安全、可观测性和评估体系，是目前最完整的工程化方案之一。
